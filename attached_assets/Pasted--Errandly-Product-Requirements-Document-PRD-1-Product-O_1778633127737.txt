# Errandly — Product Requirements Document (PRD)

## 1. Product Overview

Errandly is a hyperlocal digital marketplace that connects customers who need physical errands completed with verified local runners who can perform those errands for payment. The platform emphasizes trust, user safety, escrow-backed transactions, and real-time visibility.

## 2. Product Vision

To become the most trusted local errand execution platform, enabling users to outsource physical tasks safely, quickly, and affordably.

## 3. Goals

* Provide a reliable way for users to delegate physical errands.
* Create earning opportunities for verified runners.
* Ensure end-to-end security through KYC, escrow, tracking, and dispute handling.
* Build a scalable marketplace for individuals and businesses.

## 4. User Roles

* Customer
* Runner
* Admin
* Verification Officer

## 5. Core Features

### Customer Features

* Register and verify identity
* Create errands
* Fund wallet and pay for tasks
* Track assigned runner in real time
* Chat with runner
* Confirm completion
* Rate runner
* Open disputes

### Runner Features

* Apply and complete KYC
* Browse and accept errands
* Navigate to pickup/delivery locations
* Upload proof of task completion
* Receive earnings
* Withdraw funds
* Rate customers

### Admin Features

* User management
* Runner approvals
* KYC review
* Errand monitoring
* Payment oversight
* Dispute resolution
* Incident response
* Analytics and reporting

# Errandly — Software Requirements Specification (SRS)

## 1. Introduction

This document specifies the software requirements for the Errandly platform across web and mobile applications.

## 2. System Scope

The software system shall support creation, assignment, execution, monitoring, and completion of errands between customers and runners in a secure digital environment.

## 3. Functional Requirements

### FR-1 User Authentication

* Users shall register with email/phone.
* Users shall log in securely.
* Password reset shall be supported.
* Sessions shall be managed securely.

### FR-2 Identity Verification

* Users shall upload KYC documents.
* Runner accounts shall require approval before activation.
* Admins shall approve/reject submissions.

### FR-3 Errand Management

* Customers shall create errands.
* Runners shall accept errands.
* Customers shall track progress.
* Tasks shall support lifecycle states.

### FR-4 Payment Management

* Users shall fund wallets.
* Payments shall be held in escrow.
* Funds shall release upon completion.
* Refund workflows shall be supported.

### FR-5 Messaging

* Users shall exchange messages.
* Voice notes and image sharing should be supported.

### FR-6 Ratings and Reviews

* Users shall rate completed interactions.
* Trust scores shall update automatically.

### FR-7 Disputes

* Users shall report incidents.
* Admins shall review evidence.
* Resolution outcomes shall be logged.

## 4. Non-Functional Requirements

### Security

* KYC verification mandatory for runners.
* OTP verification for handoffs.
* Encrypted communication.
* Device session tracking.
* Audit logs for all financial actions.

### Performance

* Support concurrent active errands.
* Map updates in near real time.
* Response times under 2 seconds for key operations.

### Reliability

* Transactions must be atomic.
* Failed payments must roll back safely.
* Task state changes must be logged.

### Scalability

* System should support expansion to multiple cities.
* Role-based modular design.

## 5. Use Cases

* Create errand
* Accept errand
* Cancel errand
* Track runner
* Confirm delivery
* Raise dispute
* Withdraw earnings
* Suspend user
* Approve KYC

## 6. Edge Cases

## 7. Assumptions

* Users possess smartphones.

## 8. Future Extensions

# Errandly — Business Rules & Workflow Document

## 1. Core Operational Rules

### User Eligibility

* Customers may create errands only after basic identity verification.
* Runners may accept errands only after full KYC approval.
* Suspended or flagged users cannot initiate or accept tasks.

### Geographic Service Rules

* Errands are limited to supported service zones.
* Runners may only accept tasks within configured service radius.
* Admin can override and manually reassign across zones.

## 2. Errand Lifecycle Workflow

### Stage 1: Creation

1. Customer creates errand.
2. Customer enters task details, addresses, schedule, and budget.
3. Customer funds the task amount plus platform fee.
4. Payment is held in escrow.
5. Errand status becomes `posted`.

### Stage 2: Assignment

1. System identifies nearby verified runners.
2. Eligible runners receive notifications.
3. First accepted runner is assigned.
4. Errand status becomes `accepted`.
5. Customer receives runner details.

### Stage 3: Execution

1. Runner travels to pickup location.
2. Runner checks in on arrival.
3. Customer provides pickup OTP if physical handoff required.
4. Task begins.
5. GPS tracking activates.
6. Chat/call channel remains available.

### Stage 4: Completion

1. Runner uploads proof (photo, receipt, note).
2. Runner marks task completed.
3. Customer verifies outcome.
4. Customer enters completion OTP.
5. Escrow releases funds.
6. Errand status becomes `completed`.

## 3. Cancellation Rules

### Customer Cancellation

* Before assignment: full refund.
* After assignment but before pickup: service fee deducted.
* After pickup: cancellation triggers dispute review.

### Runner Cancellation

* Before acceptance confirmation: no penalty.
* After acceptance: trust score reduction.
* After pickup: severe penalty and investigation.

## 4. Dispute Rules

### Dispute Triggers

* Item not delivered.
* Item damaged.
* Wrong task execution.
* Harassment or misconduct.
* Fraudulent completion.
* Missing payment.

### Dispute Handling

1. User submits dispute.
2. Escrow freezes.
3. Admin reviews evidence.
4. Parties may submit additional proof.
5. Admin issues decision.
6. Refund/release applied.
7. Account penalties updated.

## 5. Trust Score Rules

Trust score affects task assignment priority.

### Factors

* Completion rate
* Average rating
* Cancellation rate
* Dispute history
* Response time
* Account age
* Verification confidence

### Penalties

* Fake proof uploads
* Frequent cancellations
* Late arrival
* Safety incidents
* Abuse reports

## 6. Safety Workflow

### Panic Event

1. User presses panic button.
2. Task immediately flagged.
3. Admin alerted.
4. Live location snapshot stored.
5. Communication logs preserved.
6. Emergency contact notified.
7. Manual review initiated.

## 7. Financial Workflow

### Payment States

* pending_funding
* funded
* in_escrow
* released
* refunded
* frozen

### Withdrawal Rules

* Runners can withdraw only completed earnings.
* Pending disputes block affected payouts.
* Admin may freeze suspicious wallets.

* Suspend account

* Issue manual refunds
* Override verification status
